Pothole Detection System

An AI road-inspection system. It looks at road photos, videos or a live camera, finds every pothole, rates how dangerous each one is, gives the road a score from 0 to 100, estimates the repair cost, and keeps a record of every inspection until the road is repaired.

3YOLO AI models working together
0–100Road Condition Index
4severity levels, Low → Critical
~0.3 sper photo on a laptop CPU
Say this when someone asks “what is your project?”

“Our project is an AI system that helps a city’s road department find and fix potholes. An inspector uploads a road photo or video, or points a camera at the road. Three YOLO deep-learning models find the potholes, and the system grades each one from Low to Critical, gives the road a condition score out of 100, and estimates the repair cost and how soon it must be fixed. Every inspection is saved, so the department can see the worst roads first and track each repair from Open to Scheduled to Repaired.”

The problem it solves

Slow

Inspectors check roads by eye and write notes by hand. It takes a long time to cover a city.

Not consistent

Two people judge the same pothole differently. There is no common score.

No priority

Without numbers it is hard to decide which road to repair first or how much money is needed.

Our system gives the same, fast, measurable answer every time: how many potholes, how bad, which road first, and roughly what it will cost.

Section 2

How to run it

One command starts everything. Open a terminal in the project folder and run:

Terminal
cd ~/Desktop/Pothole-Detection-System-main && ./start.sh

The browser opens http://localhost:8000 by itself. To stop it, press Ctrl + C in that terminal.

What start.sh does, in order

Installs what is missing

Only the first time: makes the Python environment (.venv) and installs the website packages (node_modules).

Builds the website

Only when a file in frontend/app changed. Next.js turns the code into plain web files in frontend/out.

Frees the port

If an old copy is still running on port 8000, it stops it, so the new one can start.

Starts the server

Runs backend/server.py. It shows the website and runs the AI, all on one address.

How the parts connect

There are two parts. The website (Next.js) is what you see. The server (Python) runs the AI and stores data. They talk over HTTP, the same way any website talks to its server.

WebsiteNext.js · Reactfrontend/app
photo →
ServerFastAPIserver.py
image →

boxes →
Reportscores, repair, drawingreport.py

DatabaseSQLite filehistory.db

The answer travels back the same way: the server sends the marked photo, the scores and the repair estimate to the website as JSON (text data), and the website shows it.

One inspection, step by step

You pick a photo

PhotoView.js tells page.js, which calls analyzePhoto() in api.js. It sends the photo + settings + road details to POST /api/analyze.

The server reads the photo

read_photo() turns the bytes into an image. read_gps() reads the location hidden in the photo, if there is one.

The AI finds potholes

Detector.find() runs the models, merges their boxes and removes duplicates. The result is remembered, so the same photo is not checked twice.

The report is built

build_report() filters weak boxes, gives each pothole a danger score and level, scores the road, estimates the repair, and draws the boxes.

It is saved and sent back

database.save_scan() stores the inspection and returns its number. The website shows the report.

detector.py — finds the potholes

Loads the YOLO models and runs them. Main functions:

FunctionWhat it does

backend/detector.py — Detector.find()
main_results = [run_model(model, image) for model in self.main_models]      # 1. every main model looks
helper_result = run_model_with_tiles(self.helper_model, image)          # 2. helper looks (with tiles)
boxes, scores = merge_boxes(main_results, helper_result)                # 3. join the answers
boxes, scores = remove_duplicates(boxes, scores)                        # 4. remove duplicates

report.py — turns boxes into a report

Takes the boxes and makes everything the website shows: danger score and level per pothole, the Road Condition Index, the repair estimate, and the photo with boxes drawn on it.

backend/report.py — danger_score()
def danger_score(box, width, height, confidence):
    x1, y1, x2, y2 = box
    size_share = (x2 - x1) * (y2 - y1) / (width * height)            # part of the photo it covers
    size   = min(size_share / 0.05, 1.0) * 50                        # up to 50 points
    centre = (1 - abs((x1 + x2) / 2 - width / 2) / (width / 2)) * 20 # up to 20 points
    close  = ((y1 + y2) / 2 / height) * 15                            # up to 15 points
    sure   = confidence * 15                                          # up to 15 points
    return round(size + centre + close + sure, 1)

database.py — remembers every inspection

Uses SQLite, a database that is just one file (history.db), built into Python. One table, scans, one row per inspection. save_scan() adds or updates a row, update_scan() changes the status, history() returns all rows plus totals for the Overview.

Each photo gets a fingerprint (SHA-1 hash of its bytes). Checking the same photo again updates the same row instead of making a duplicate, and it never resets the repair status.

server.py — the API

Built with FastAPI. It receives requests from the website, calls the detector and report, saves to the database and answers with JSON. It also serves the built website, so everything runs on one address. Details of each endpoint are in Section 10.

Section 8

How the AI finds potholes

YOLO (“You Only Look Once”) is a deep-learning model for object detection. It looks at the whole image once and returns boxes around the objects it was trained on — here, potholes — each with a confidence from 0 to 1.

The three models

ModelFileSizeGood atSource
YOLOv8sbest.pt21 MBFast and accurate; used for video and live cameraSamdutse/pothole-yolov8
YOLOv9cpothole_yolov9c.pt49 MBBigger model, a second opinionEngJamesO/pothole-detector (MIT)
YOLO11n (PotholeNet)potholenet_yolo11n.pt5 MBWater-filled potholes on rough roadsKarn815833/PotholeNet-YOLO11n (MIT)

These are pre-trained pothole models published on Hugging Face. The project also includes a training tool (tools.py train) to train your own model on your own photos.

The Ensemble engine, step by step

Two main models look

YOLOv8s and YOLOv9c each return their boxes. We keep everything above 1% confidence and filter later, so the slider can change the result without running the AI again.

The helper looks closer

PotholeNet checks the whole photo and, for photos larger than 960 px, also 640 px squares (“tiles”) that overlap by 25%. Small, far-away potholes are no longer lost when the photo is shrunk.

Weighted Box Fusion merges the answers

Boxes that overlap more than 45% (IoU > 0.45) are the same pothole. They become one box, placed at the confidence-weighted average position.

Duplicates are removed

If 70% of a box lies inside a stronger box, it is a duplicate and is dropped.

The road check removes false alarms

With High sensitivity, boxes that are more than 50% green (grass, trees) or tall and more than 40% white (lane paint) are thrown away. Colours are read in HSV (hue, saturation, brightness).

How the merged score is calculated

Both models see the pothole: 0.80 and 0.60 → (0.80 + 0.60) ÷ 20.70
Only one model sees it: 0.80 → 0.80 ÷ 20.40
Only the helper sees it: 0.90 × 0.7 (we trust it a bit less alone)0.63

So a pothole that both models agree on scores higher. This is why the Ensemble makes fewer mistakes than one model.

GPS location

Phone cameras hide extra data inside a photo, called EXIF. When location is on, it includes the GPS position as degrees, minutes and seconds. read_gps() in server.py reads it with the Pillow library and turns it into a normal latitude/longitude, which the report links to Google Maps.

Section 11

Speed and keeping the laptop cool

Half the CPU

The AI may use only half the CPU cores (max 4): CPU_THREADS in config.py. The laptop stays usable and cooler.

One job at a time

A lock (ai_lock) lets only one AI job run at once, so many requests cannot overload the CPU.

Results remembered

The same photo + engine is never checked twice. Moving the confidence slider only re-filters the saved boxes: instant.

Smart video

Frames are shrunk to 640 px, only every Nth frame is checked, and at most 5 checks per second.

Smooth live camera

The video plays directly at full speed. Only a small 512 px copy goes to the AI, and only box positions come back (no picture), drawn on a layer on top. Up to 6 AI updates per second, ~60 ms each.

No extra server

The website is built once into plain files that Python serves. No Node.js server keeps running in the background.

Key words explained

TilingCutting a large photo into smaller overlapping squares so small objects keep their detail.

About the project
What is your project?

An AI road-inspection system. It finds potholes in photos, videos and a live camera with three YOLO models, grades each pothole Low to Critical, gives the road a 0–100 condition score, estimates the repair cost and deadline, and tracks every inspection until it is repaired.

Who will use it?

A city or municipal road department: field inspectors create inspections, and engineers or managers use the Overview and Inspections pages to decide which road to repair first and how much budget is needed.

What problem does it solve?

Manual inspection is slow, not consistent between people, and gives no clear priority. Our system gives a fast, repeatable score for every road and a ranked priority list with a cost estimate.

What are the main features?

Photo inspection with a report, video survey, real-time live camera, a dashboard with a priority queue, an inspection list with repair status (Open → Scheduled → Repaired), repair cost estimates, GPS location from photos, PDF printing, CSV export and comparison of 4 AI engines.

Which technologies did you use?

Python, YOLO via the Ultralytics library, PyTorch, OpenCV for images and video, FastAPI for the server, SQLite for the database, and Next.js with React for the website.

The AI
What is YOLO and why did you choose it?

YOLO (“You Only Look Once”) is a deep-learning object detector that finds all objects in one pass over the image. We chose it because it is fast enough for video and live camera on a normal laptop, accurate, and easy to use through the Ultralytics library.

Why not Faster R-CNN or another model?

Two-stage models like Faster R-CNN can be accurate but are slower. We need real-time speed for the live camera on a laptop CPU, so a one-stage model like YOLO is the better fit.

Why three models instead of one?

Each model makes different mistakes. When two models agree, we are more confident; the third model (PotholeNet) is good at water-filled potholes and adds ones the others miss. Together the Ensemble has the highest recall (78–80%).

Did you train the models yourself?

The three detection models are pre-trained pothole models published on Hugging Face (YOLOv8s by Samdutse, YOLOv9c by EngJamesO, PotholeNet YOLO11n by Karn815833). Our work is how we combine them (ensemble, tiling, filtering), the scoring, the repair planning and the full system. The project also contains a training tool (tools.py train) and dataset cleaning tools to train our own model.

What is Weighted Box Fusion?

A way to merge boxes from several models. Boxes that overlap more than 45% are treated as the same pothole and replaced by one box at their confidence-weighted average position. The score is the sum of the models’ scores divided by the number of models, so agreement gives a higher score.

What is IoU?

Intersection over Union: the overlapping area of two boxes divided by the total area they cover. 0 means no overlap, 1 means identical boxes. We use 0.45 to decide if two boxes are the same pothole.

What is the confidence threshold?

The minimum confidence a box needs to be shown. High sensitivity uses 15% (finds faint, far potholes), Balanced uses 25% (only surer ones). The user can change it with a slider.

Why do you cut big photos into tiles?

YOLO shrinks every image to 640 px. On a big photo, a small far-away pothole becomes just a few pixels and is missed. Checking 640 px squares at full resolution keeps those details. We only keep small boxes from tiles and ignore boxes cut by a tile edge.

How do you reduce false detections?

Four ways: the confidence threshold, agreement between models (Ensemble), removing duplicate boxes, and a colour check that drops boxes that are mostly green (grass) or tall and white (lane markings).

What are precision and recall?

Precision: of the boxes we drew, how many are real potholes. Recall: of all real potholes, how many we found. F1 combines both into one number.

What accuracy did you get?

On 100 labelled photos with 269 potholes, the Ensemble found 78% of potholes (80% with High sensitivity) and gave no false alarm on a clean road. YOLOv8s alone has the best precision (0.84). Ensemble precision shows 0.72, but many of its extra boxes are real potholes that were not labelled in the test set.

Why do you care more about recall?

For road safety, missing a dangerous pothole is worse than checking one extra box. An inspector can quickly ignore a wrong box, but a missed pothole may cause an accident.

What is mAP50?

Mean Average Precision at IoU 0.5: the standard score for detection models. It summarises precision at all confidence levels when a correct box must overlap the real pothole by at least 50%. The training tool prints it.

Scores and repair
How do you decide how dangerous a pothole is?

A danger score from 0 to 100: size in the photo (up to 50), how close it is to the road centre (20), how close to the camera (15), and AI confidence (15). 0–19 Low, 20–39 Medium, 40–59 High, 60+ Critical.

Why those weights (50/20/15/15)?

Size matters most for damage, so it has half the points. Position matters because cars drive in the centre and near potholes are hit first. Confidence makes sure uncertain boxes count less. The weights are simple and explainable and are kept in code so they can be tuned with real repair data later.

What is the Road Condition Index?

A score from 0 to 100 for the whole road. It starts at 100 and loses 3, 7, 15 or 35 points for each Low, Medium, High or Critical pothole. 85+ is Excellent, below 30 is Dangerous.

How do you estimate the repair cost?

We assume a road photo shows about 20 m² of road, so a pothole covering 3% of the photo is about 0.6 m². Depth is assumed from the level (2–8 cm). That gives asphalt in kg, crew hours and cost: ₹500 fixed plus a rate per m² (₹600–1,800 by level). It is a planning estimate; all values are in config.py.

Can it measure the real depth or size?

Not exactly. One normal photo has no depth information. We estimate size from the photo and assume depth by severity. Exact measurement would need a depth camera, stereo cameras or LiDAR, which is future work.

How is the repair deadline decided?

From the worst pothole on the road: Critical within 24 hours, High within 7 days, Medium within 30 days, Low at the next routine check.

The system
Explain the architecture.

A Next.js website sends the photo over HTTP to a Python FastAPI server. The server runs the detector (3 YOLO models), builds the report (scores, repair estimate, drawing), saves the inspection in SQLite and sends the result back as JSON. The same server also serves the website, so everything runs on one address.

Why FastAPI?

The AI runs in Python, so the server is in Python too. FastAPI is quick to write, fast, checks input types automatically, handles file uploads, and supports streaming answers for the live video results.

Why Next.js?

It lets us build the website from React components (one per page and small shared parts) and export it as plain files, which our Python server can serve. No separate Node.js server has to keep running.

How does the website send a photo to the server?

As FormData (like a form with a file upload) using fetch() to POST /api/analyze. The answer is JSON, and the marked photo comes back as a base64 text image.

Which database do you use, and why?

SQLite. It is a full SQL database stored in one file and built into Python, so nothing extra has to be installed or run. One table, scans, stores each inspection.

How do you stop duplicate inspections?

Each photo gets a SHA-1 fingerprint of its bytes, stored as a unique key. Checking the same photo again (for example after moving the slider) updates the same row with an “upsert” and keeps its repair status.

How does GPS location work?

Phone photos with location turned on store GPS inside the EXIF data. The server reads it with Pillow, converts degrees/minutes/seconds to decimal latitude and longitude, saves it, and the report links to Google Maps.

How does the live camera work, and why is it smooth?

The browser shows the camera video directly at full speed. In the background it sends a small 512 px copy of the current frame to the server, which runs the fastest model (YOLOv8s, about 60 ms) and returns only box positions. The website draws those boxes on a transparent canvas over the video. The next frame is sent when the answer arrives, up to 6 per second.

How does the video survey work?

The video is uploaded, the server opens it with OpenCV and checks every Nth frame (shrunk to 640 px). After each frame it sends one line of JSON straight away (streaming), so results appear live. At the end it saves a summary with the worst frame and the average road score.

How do you keep the laptop from overheating?

The AI uses only half the CPU cores, only one AI job runs at a time, results are remembered, video frames are shrunk and limited to 5 checks per second, and the live camera sends small frames and gets back only box positions.

What happens if the server stops?

The sidebar shows “AI server offline” and a red banner explains how to start it (./start.sh). If an older version is running, the website notices from the version number and asks for a restart.

Is it secure?

It runs locally on one computer. Sample file names are cleaned so nobody can read other files (“../” tricks are blocked), status values are checked, and SQL uses parameters, not glued text. For real city use we would add logins and user roles (future work).

Does it need the internet?

No. The models are stored in the models folder and the server runs offline. Only the Google Maps link needs the internet.

Using and changing it
How do you run the project?

Run ./start.sh in the project folder and open http://localhost:8000. It installs what is missing, builds the website and starts the server.

How do you change a setting, like the repair cost?

Edit backend/config.py. All numbers are there with comments, then restart with ./start.sh.

How would you add a new model?

Put the .pt file in models/, add it to MODEL_FILES in config.py, and add an engine to ENGINES. It then appears in the engine menu and in Model comparison.

How would you train your own model?

Collect road photos, label potholes in YOLO format, clean the labels with tools.py dataset-clean, then run tools.py train data.yaml. It uses flips, mosaic and brightness changes (augmentation) and prints precision, recall and mAP50.

What is the YOLO label format?

One text file per image, one line per pothole: class x_center y_center width height, all as fractions of the image size (0 to 1).

Limits and future
What are the limitations?

Size and cost are estimates (no real depth); accuracy drops at night, in heavy rain, or with motion blur; shadows and patches can be confused with potholes; and it runs on one computer without user accounts.

What would you add next?

A map of all potholes, a mobile app for inspectors, logins and roles, training on local Indian roads, depth measurement with stereo cameras or LiDAR, a vehicle-mounted camera that inspects while driving, and automatic complaint reports to the municipality.

Why is this useful for society?

Potholes damage vehicles and cause accidents, especially for two-wheelers. Finding them early, ranking them and planning the budget helps cities repair the most dangerous roads first.

What was the hardest part?

Combining three models without double-counting potholes (solved with Weighted Box Fusion and duplicate removal), finding small far-away potholes (solved with tiling), and making the live camera smooth on a laptop (solved by drawing boxes over the live video instead of waiting for processed images).
